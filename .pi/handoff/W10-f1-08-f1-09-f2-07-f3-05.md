### Decisões de design

1. **`TextureSource.defaultOptions.scaleMode = 'nearest'` e `autoGenerateMipmaps = false` ANTES do primeiro `Assets.load`.** Configuração GLOBAL aplicada na fábrica `createPlayer`.

2. **Escala do palco INTEIRA.** `stage.scale.set(stageScale)` com valor inteiro (default 2).

3. **fps no sidecar `.pixellab.json`.** O campo `fps` vive em `SidecarData`, não no JSON do Pixi. `animationSpeed = fps / 60`.

4. **Âncora do sidecar.** Se `anchorSource === 'padrao'`, é emitido `console.warn` informando que a âncora foi escolhida pela API e sugerindo definir uma âncora customizada.

5. **PreviewAction** é o contrato para carregar uma ação: `atlasUrl`, `sidecar`, `framesByDirection`.

### Limitações conhecidas

- O player NÃO está integrado ao `main.ts` nem ao fluxo de geração. A integração é uma task separada.
- A resolução de texturas usa `Assets.load({ src: url, loadParser: 'loadTextures' })` — assume que as texturas são URLs de imagem.
- O player não implementa loop de animação com delta time; usa o ticker do PixiJS para detetar mudanças de frame.

## F1-09 — Teste de idempotência ponta a ponta do builder

### Arquivos

- `tools/character-builder/server/idempotence.test.ts` — 6 testes

### API pública

(Nenhuma — é um teste.)

### Decisões de design

1. **CountingClient** — estende `PixelLabClient` e conta chamadas por `path` num `Map<string, number>()`. Interceta `/rotate`, `/create-character-with-8-directions` e `/animate-character`.

2. **Cobertura de endpoints:** rotate (3 chamadas na 1ª execução, 0 na 2ª), animate (1 chamada na 1ª, 0 na 2ª), e ledger (não ganha linhas na 2ª passada).

3. **Seed diferente força regeneração:** testado que mudar o seed de 42 para 99 produz novas chamadas (>0).

4. **Ledger medido por contagem de linhas** do ficheiro ndjson. Primeira execução escreve N linhas, segunda mantém as mesmas N.

### Limitações conhecidas

- O teste NÃO cobre `create-character-with-8-directions` diretamente porque esse endpoint é chamado por `api.ts` (que depende do ficheiro `studio.json`). O teste cobre `rotateCardinals` e `animateCharacter` que são os blocos com idempotência implementada.
- O `CountingClient` não simula jobs completos — devolve `status: 'completed'` imediatamente.

### Arquivos

### API pública


#### wall.ts

```ts
export type ElementoAresta = 'parede' | 'porta' | 'pilar' | 'escada';

export function arestaProxima(sx: number, sy: number, cellX: number, cellY: number, z: number, geom?: GeometriaProjecao): LadoProximo | null
export function colocarNaAresta(edges: EdgeStore, x: number, y: number, z: number, lado: EdgeSide, tipo: ElementoAresta): WallResult
export function removerDaAresta(edges: EdgeStore, x: number, y: number, z: number, lado: EdgeSide): WallResult
export function elementoNaAresta(edges: EdgeStore, x: number, y: number, z: number, lado: EdgeSide): string | undefined
```

### Decisões de design

1. **Operações sobre o modelo, não sobre a tela.** Todas as funções recebem `BlockStore`/`EdgeStore` e devolvem novas instâncias (imutabilidade). O estado nunca é mutado diretamente.

2. **Desfazer/refazer.** As funções devolvem o estado anterior + o novo estado, permitindo que um sistema de comandos (a implementar na integração) faça undo/redo.

3. **Clone via RLE.** `BlockStore` e `EdgeStore` são clonados via `fromRle(toRle())` / `fromEntries(toEntries())` — a forma canónica de cópia profunda.

4. **Deteção de proximidade da aresta.** `arestaProxima` calcula a distância em píxeis do cursor ao ponto médio de cada aresta da célula (N, S, L, O). Se a distância for < 12 px, o cursor está "perto da aresta" e deve mudar para modo parede.

5. **Porta, pilar, escada** são tratados como tipos de aresta (`ElementoAresta`), não como objetos separados. O `EdgeStore` armazena o tipo como string.

6. **Todo texto em pt-BR.** Mensagens de retorno usam português.

### Limitações conhecidas

- As ferramentas NÃO estão integradas ao `app.ts` do map-builder. A integração (registar eventos de clique, chamar `pick` + ferramenta ativa) é uma task separada.
- O undo/redo NÃO está implementado nestes módulos — as funções são os blocos de construção. O sistema de comandos que orquestra undo/redo deve ser implementado na integração.
- A geometria (`GeometriaProjecao`) está inline no `wall.ts`, duplicando a que existe em `picking.ts` e `renderer.ts` — isto é intencional para evitar a dependência de `iso-core/geometry.ts` → `project.ts` → `node:crypto` (incompatível com browser).
- Não há testes unitários para estas ferramentas (o cartão não os pedia). A verificação é manual ou via integração futura.

## F3-05 — Teste headless de traço de entrada

### Arquivos

- `packages/iso-core/src/trace.ts` — Motor de traço (runTrace)
- `packages/iso-core/src/trace.test.ts` — 8 testes
- `packages/iso-core/test-fixtures/mapa-degraus.json` — Fixture de mapa

### API pública

```ts
export interface TraceFrame {
  readonly duration: number;
  readonly input: MovementInput;
}

export interface TraceResult {
  readonly finalState: MovementState;
  readonly totalSteps: number;
  readonly totalTime: number;
  readonly blocked: boolean;
  readonly blockedAt?: { readonly x: number; readonly y: number; readonly z: number };
}

export function runTrace(map: CollisionMap, startX: number, startY: number, startZ: number, frames: readonly TraceFrame[], config?: MovementConfig): TraceResult

export function dirInput(dx: number, dy: number): MovementInput
export function jumpInput(dx: number, dy: number): MovementInput
export function stepUpInput(dx: number, dy: number): MovementInput
export function stepDownInput(dx: number, dy: number): MovementInput
```

### Decisões de design

1. **Integração de movimento + colisão.** `runTrace` integra `movement.ts`, `collision.ts`, `step-up.ts` e `jump.ts` num único loop de simulação determinístico.

2. **Passo fixo manual.** O loop gere o acumulador manualmente (sem usar `step()` de `movement.ts`) para ter controlo fino sobre step-up e pulo a cada passo.

3. **Colisão durante pulo.** Durante o pulo (`airborne=true`), a verificação de walkability (`canEnter`) é relaxada: não exige suporte (bloco em z-1). Apenas verifica se o destino não tem bloco.

4. **Colisão com `zDest` durante pulo.** A resolução de colisão usa `jump.zDest` (nível mais alto) durante o pulo, permitindo "pular sobre" obstáculos.

5. **Step-up prioriza a direção do input.** `tryStep` ordena as direcções cardeais pela proximidade ao ângulo do input, garantindo que o step-up ocorre na direcção pretendida.

6. **Determinismo verificável.** O teste de determinismo executa o mesmo traço duas vezes e compara todos os campos do resultado — posição, z, totalSteps, blocked, blockedAt.

### Limitações conhecidas

- O bloqueio por `blockedAt` regista a célula anterior ao bloqueio, não a aresta exacta.
- O step-up pode ocorrer "antecipadamente" (antes de entrar na célula adjacente), o que é um comportamento válido mas pode surpreender.
- O `runTrace` não suporta pathfinding — apenas move na direção do input.
