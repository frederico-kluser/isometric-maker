## F1-04 — Leitura de rotation_urls por chave

### Arquivos

- `tools/character-builder/server/frames.ts` — `parseAndWriteFrames(response, scope, key, assetsDir)`
- `tools/character-builder/server/frames.test.ts` — 7 testes
- `tools/character-builder/server/api.ts` — `generateBase` usa `parseAndWriteFrames` em vez de `extractImages` + `writeFrames`

### API pública

```ts
export class UnknownDirectionError extends Error { direction: string }
export class MissingDirectionError extends Error { direction: Direction }
export interface FramesResult { frames: Record<string, string[]>; hasSkeletons: boolean }
export async function parseAndWriteFrames(response: unknown, scope: string, key: string, assetsDir: string): Promise<FramesResult>
```

### Decisões de design

1. **Itera DIRECTIONS na saída, não Object.keys(rotation_urls).** Isto garante que a ordem das chaves no resultado é sempre canónica, independentemente da ordem no payload.
2. **hasSkeletons** regista se o campo `skeletons` veio populado (array não vazio). Só loga no console — a E5 tratará de processar.
3. **Erros nomeados** (UnknownDirectionError, MissingDirectionError) para que o caller possa distingui-los sem parse de string.


Critérios:
- Payload com ordem invertida → mesmo resultado ✓
- Payload faltando 'west' → MissingDirectionError ✓

### API pública



### Decisões de design

1. **Session tracking em memória.** `sessionSpentUsd` acumula em memória e zera no restart do servidor. O tracking mensal lê o ledger ndjson.
2. **Botão Confirmar começa desabilitado.** Quando `report.requiresConfirmation === true`, o botão fica 2 segundos desabilitado com contagem regressiva ("Confirmar (2s)", "Confirmar (1s)", "Confirmar").
3. **O diálogo é uma função pura do DOM.** Cria overlay + dialog, devolve Promise. Sem framework.
4. **"0 de N a gerar · N em cache · US$ 0,00"** — o template sempre mostra o denominador.

### Limitações conhecidas

- O diálogo NÃO está integrado no flow de geração do `main.ts` — o card F1-06 pede o componente, não a integração. Para integrar: chamar `GET /api/estimate` antes de `POST /api/generate`, mostrar o diálogo, e só submeter se `confirmed === true`.

## F2-03 — Chave de profundidade x+y+z

### Arquivos

- `packages/iso-core/src/depth.ts` — `depthKey`, `depthKeyForEdge`, `compareDepth`, `sortByDepth`
- `packages/iso-core/src/depth.test.ts` — 26 testes

### API pública

```ts
export interface DepthCell { x: number; y: number; z: number }
export interface DepthEdge { x: number; y: number; z: number; lado: EdgeSide }
export type DepthItem = { kind: 'cell'; ... } | { kind: 'edge'; ... }

export function depthKey(cell: DepthCell): number              // x + y + z
export function depthKeyForEdge(edge: DepthEdge): number       // x + y + z ± 0.5
export function compareDepth(a: DepthItem, b: DepthItem): number
export function sortByDepth<T extends DepthItem>(items: T[]): T[]
```

### Decisões de design

1. **Paredes a meia-célula:** N/L = +0.5, S/O = −0.5. Duas células vizinhas que partilham uma aresta produzem a mesma chave (consistência verificada).
2. **Tie-breaking:** y, depois x, depois z. Declarado e determinístico.
3. **Sprite alto é limitação conhecida.** O teste demonstra a falha e documenta-a. A correcção requer metadata de altura visual no renderer (fora do escopo deste módulo).

## F3-01 — Movimento contínuo em xy, discreto em z

### Arquivos

- `packages/iso-core/src/movement.ts` — `step`, `createMovementState`, `MovementState`, `MovementInput`, `MovementConfig`
- `packages/iso-core/src/movement.test.ts` — 24 testes

### API pública

```ts
export interface MovementState { pos: Vec2; z: number; vel: Vec2; vz: number | null; jumpTime: number; airborne: boolean; facing: number; accumulator: number }
export interface MovementInput { dir: Vec2; jump: boolean; stepUp: boolean; stepDown: boolean }
export interface MovementConfig { speed: number; fixedDt: number; jumpDuration: number; jumpHeight: number; stepCooldown: number }
export const DEFAULT_CONFIG: MovementConfig

export function createMovementState(x: number, y: number, z: number): MovementState
export function step(state: MovementState, input: MovementInput, dt: number, config?: MovementConfig): MovementState
```

### Decisões de design

1. **Passo fixo com acumulador.** `step` acumula `dt`, calcula `Math.floor(total / fixedDt)` passos, executa-os, e guarda o remainder. Isto evita o problema de precisão do while com subtracção repetida de 1/60.
2. **z discreto.** `stepUp` e `stepDown` mudam z imediatamente em ±1. `jump` sobe `jumpHeight` níveis imediatamente e marca `airborne = true`. Durante o pulo, z não muda. Após `jumpDuration`, `airborne → false`.
3. **Função pura.** `step` e `fixedStep` não tocam em DOM, rede, ou PixiJS. Determinismo verificado.

## F3-02 — Colisão de célula e de aresta

### Arquivos

- `packages/iso-core/src/collision.ts` — `canEnter`, `canCross`, `CollisionMap`, `CollisionCell`
- `packages/iso-core/src/collision.test.ts` — 26 testes

### API pública

```ts
export interface CollisionCell { x: number; y: number; z: number }
export interface CollisionMap { hasBlock(x,y,z): boolean; hasEdge(x,y,z,lado): boolean }

export function canEnter(map: CollisionMap, x: number, y: number, z: number): boolean
export function canCross(map: CollisionMap, from: CollisionCell, to: CollisionCell): boolean
```

### Decisões de design

1. **canEnter e canCross SEPARADAS.** `canEnter` verifica walkability da célula (não ocupada + suporte). `canCross` verifica travessia da aresta (destino entrável + sem parede).
2. **Arestas verificadas nos DOIS lados.** `hasWallBetween` consulta tanto `hasEdge(from, ..., fromSide)` como `hasEdge(to, ..., toSide)`, porque o editor pode registar a parede em qualquer um dos lados.
3. **Diagonal testa AS DUAS arestas.** Movimento (dx,dy) com |dx|=|dy|=1 testa a aresta-x (entre from e midX) e a aresta-y (entre midX e to). Se qualquer uma estiver bloqueada, a diagonal falha.
4. **Interface `CollisionMap`** desacopla o motor de colisão de `BlockStore`/`EdgeStore`. Qualquer objecto com `hasBlock` e `hasEdge` serve.

## Destinatários nomeados

- **E5 (skeletons):** `hasSkeletons` no `FramesResult` indica se o campo veio populado. O campo é logado no console em `generateBase`.
- **F2-05 (renderer):** `sortByDepth` aceita `DepthItem[]` (células + arestas) e devolve a ordem de desenho. O renderer deve iterar nesta ordem.
- **F3-03 (pathfinding / integração):** `canEnter` + `canCross` + `step` formam a base para A* ou outro algoritmo de pathfinding. `CollisionMap` é a interface que o pathfinding precisa.
- **Integração do cost-dialog:** `showCostDialog` está pronta para ser chamada antes de `POST /api/generate`. A integração no `main.ts` é uma task separada.
