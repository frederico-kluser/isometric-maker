## F1-05 — Editor de esqueleto local

### Arquivos

- `tools/character-builder/src/skeleton/affine.ts` — `rescale(keypoints, alturaPx, alturaCanonica)`
- `tools/character-builder/src/skeleton/affine.test.ts` — 11 testes
- `tools/character-builder/src/skeleton/editor.ts` — `createSkeletonEditor(container, config)`

### API pública

```ts
// affine.ts
export interface Keypoint2D { readonly x: number; readonly y: number; readonly label: string; }
export function rescale(keypoints: readonly Keypoint2D[], alturaPx: number, alturaCanonica: number): Keypoint2D[]

// editor.ts
export interface SkeletonEditorConfig { readonly keypoints: readonly Keypoint2D[]; readonly alturaPx: number; readonly alturaCanonica: number; }
export interface SkeletonEditor { readonly keypoints: readonly Keypoint2D[]; readonly aprovado: boolean; readonly alturaPx: number; destroy(): void; }
export function createSkeletonEditor(container: HTMLElement, config: SkeletonEditorConfig): SkeletonEditor
```

### Decisões de design

1. **Escala em torno do centro.** `rescale` escala os keypoints em torno do centro do seu próprio bounding box, preservando o centro geométrico. Quando `alturaPx === alturaCanonica`, devolve identidade (cópia inalterada).
2. **Editor DOM puro.** O editor usa canvas 2D nativo dentro de um container DOM. Sem framework, consistente com o resto do character-builder.
3. **18 keypoints (SKELETON_LABELS).** Conectados por ossos (BONES) definidos no editor.
4. **Estado `aprovado` explícito.** Um booleano que impede edição após aprovação. O botão "Aprovar" alterna o estado. Animação NUNCA é destravada sem aprovação.
5. **ZERO chamadas de rede.** O editor e a função `rescale` são puramente locais.

### Limitações conhecidas

- O editor não persiste o estado. A integração com o fluxo de geração (enviar os keypoints para a API) é uma task separada.
- O canvas tem tamanho fixo 400×400. Redimensionamento responsivo não foi implementado.

## F2-04 — Parser de tile_rules

### Arquivos

- `packages/iso-core/src/tile-rules.ts` — `parseTileRule`, `parseTileRules`, `classifyTileHeuristic`, `classifyKit`
- `packages/iso-core/src/tile-rules.test.ts` — 29 testes
- `packages/iso-core/test-fixtures/tiles-pro-building.json` — fixture sintética

### API pública

```ts
export interface RawTileRule { tile_index, rule_type, arity, connectivity, terrains, mask }
export interface RawTilesProResponse { tile_id, kind, tiles, tile_rules }
export interface TileRule { tileIndex, ruleType, arity, connectivity, terrains, mask, activeSides }
export type TileHeuristic = { kind: 'floor' } | { kind: 'wall' } | { kind: 'doorway' } | { kind: 'pillar' } | { kind: 'staircase' } | { kind: 'unknown'; terrains: readonly string[] }

export function parseTileRule(raw: RawTileRule, maxTileIndex: number): TileRule
export function parseTileRules(response: RawTilesProResponse): TileRule[]
export function classifyTileHeuristic(rule: TileRule): TileHeuristic
export function classifyKit(rules: readonly TileRule[]): Set<TileHeuristic['kind']>

export class UnknownTileRuleFieldError extends Error { field: string }
export class InvalidTileIndexError extends Error { tileIndex: number; maxIndex: number }
```

### Suposições abertas (ABERTO)

| ID | Descrição | Local |
|----|-----------|-------|
| AB-370 | Shape completo de `tile_rules` não confirmado contra a API | tile-rules.ts |
| AB-371 | Máscara: bit0=N, bit1=L, bit2=S, bit3=O (convenção F2-02) | tile-rules.ts |
| AB-372 | Classificação de porta/pilar/escada por nome de terreno, não por campo da API | tile-rules.ts |
| AB-373 | Mask para corner/outline segue mesma convenção de bits | tile-rules.ts |
| AB-374 | `connectivity: 'other'` indica transição entre dois terrenos | tile-rules.ts |
| AB-375 | Arity 6 (hex) sem mapeamento de lados definido | tile-rules.ts |

### Decisões de design

1. **E4 não foi executado.** A fixture é sintética, baseada na descrição em prosa do spec.
2. **Campos desconhecidos → erro nomeado.** `UnknownTileRuleFieldError` é lançado para qualquer campo não reconhecido, porque `additionalProperties: true` no spec significa que campos novos podem aparecer e o parser não deve ignorá-los silenciosamente.
3. **Heurística de classificação.** Porta, pilar e escada são identificados por substring no nome do terreno (`terrains`). Se a API tiver um campo dedicado, esta heurística deve ser substituída.
4. **Mapeamento de bits documentado.** A convenção F2-02 (N=0, L=1, S=2, O=3) é usada para mapear bits da máscara para lados. Testada exaustivamente (16 combinações).

## F2-05 — Renderizador isométrico do mapa

### Arquivos

- `tools/map-builder/package.json` — pixi.js 8.19.0 exacto + @isometric-maker/iso-core
- `tools/map-builder/index.html`
- `tools/map-builder/vite.config.ts`
- `tools/map-builder/tsconfig.json`
- `tools/map-builder/src/app.ts` — Application com init assíncrono, ticker separado, fixture
- `tools/map-builder/src/renderer.ts` — `createMapRenderer(canvas, config)`

### API pública

```ts
export interface RendererConfig { geometry, stageScale, cameraOffset, backgroundColor }
export interface MapRenderer { stage: Container; app: Application; render(map: MapData): void; destroy(): void; }
export function createMapRenderer(canvas: HTMLCanvasElement, config: RendererConfig): Promise<MapRenderer>
```

### Decisões de design

1. **pixi.js 8.19.0 exacto.** Versão fixa no package.json, sem `^` ou `~`.
2. **Geometria inline.** `ProjectGeometry` e `worldToScreen` foram duplicados localmente para evitar a dependência de `project.ts` que importa `node:crypto` (não disponível no browser). Isto é uma limitação conhecida — o ideal seria iso-core separar tipos puros de código Node.js.
3. **Escala do palco INTEIRA.** `stage.scale.set(config.stageScale)` com valor inteiro (2 no exemplo).
4. **scaleMode 'nearest'** configurado por textura via `tex.source.scaleMode = 'nearest'`.
5. **Culling.** `stage.cullArea` definido com base no viewport e offset da câmara.
6. **Pool de sprites.** Sprites são reutilizados para evitar alocações por frame. Sprites não usados ficam com `visible = false`.
7. **Fixture incluída.** Um mapa 3×3 com blocos (grass, dirt, stone) e 3 paredes serve como demonstração.
8. **Teardown completo.** `destroy()` limpa texturas, sprites e a aplicação PixiJS.

### Limitações conhecidas

- As texturas são rectângulos coloridos (placeholder). A integração com texturas reais (tileset) é uma task futura.
- O `worldToScreen` está duplicado. Quando iso-core separar tipos de código Node.js, esta duplicação deve ser removida.
- O renderizador não tem testes automáticos (testes de renderização com PixiJS requerem ambiente browser com WebGL).

## F3-03 — Degrau automático

### Arquivos

- `packages/iso-core/src/step-up.ts` — `canStepUp`, `canStepDown`
- `packages/iso-core/src/step-up.test.ts` — 17 testes

### API pública

```ts
export function canStepUp(map: CollisionMap, from: CollisionCell, to: CollisionCell): boolean
export function canStepDown(map: CollisionMap, from: CollisionCell, to: CollisionCell): boolean
```

### Decisões de design

1. **Função única e citável.** `canStepUp` implementa a condição exacta: `to.z === from.z + 1` E `canEnter(destino)` E sem parede na aresta.
2. **Aresta verificada directamente.** `canCross` não é usado porque exige que a célula de destino ao mesmo z seja entrável — o que falha quando o destino tem um bloco de suporte em `from.z`. Em vez disso, `hasWallAt` verifica paredes nos DOIS níveis (`from.z` e `to.z`).
3. **Descida permite múltiplos níveis.** `canStepDown` aceita qualquer `to.z < from.z`, não apenas `z−1`. Isto permite saltar de plataformas.
4. **Guarda `from.z < 0`.** Posições abaixo do chão são rejeitadas.
