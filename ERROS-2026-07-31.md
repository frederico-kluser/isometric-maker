Isso é uma leitura errada da [ADR 0012](docs/adr/0012-guard-de-orcamento-informativo.md). "Informa e

**Reparo mais curto:** `main.ts` chama `/api/estimate`, passa o resultado a `showCostDialog`, e só
POSTa `generate` se `confirmed === true`. O servidor deveria além disso exigir um token de
confirmação no corpo, senão qualquer aba aberta gera.

## 2. O POST que cobra é retentado até seis vezes

`tools/pixellab-pipeline/src/api.ts:93` · `:20` · `:138`

`submit()` cai no `request()` genérico, que usa `maxAttempts ?? 6` e retenta em qualquer código de
`TRANSIENT = {408, 409, 425, 429, 500, 502, 503, 504, 529}`. Para um `GET` isso está certo. Para um
`POST` que **cobra**, não: se o servidor processou a geração e cobrou, mas a resposta se perdeu num
502 ou num timeout de rede, a retentativa submete de novo e cobra de novo.

`VERIFICADO` — a API não oferece chave de idempotência:

```bash
cd /home/ondokai/Projects/isometric-maker
grep -oiP '"[^"]*idempot[^"]*"' tools/pixellab-pipeline/openapi/openapi-v2.json | sort -u
#  (vazio)
```

O cabeçalho do `queue.ts:9` promete *"A job whose id we hold is NEVER resubmitted"* — e cumpre. Mas o
caso perigoso é o outro: o job cujo id **nunca chegou até nós**, porque a resposta se perdeu. Esse é
resubmetido, e o módulo não tem como saber.

`LEITURA` — não reproduzi contra a API real (exigiria gastar). O que provei é que o código retenta
POST em 5xx e que o spec não tem chave de idempotência. Se a PixelLab cobra no *aceite* da requisição
ou só na conclusão do job é coisa que o spec não diz, e eu **não verifiquei**.

**Reparo mais curto:** `submit()` passar `maxAttempts: 1` para os códigos 5xx e manter retentativa só
em 429/529 (que são "ainda não aceitei", não "aceitei e falhei"). Ou registrar o `specHash` numa
tentativa-em-voo no `QueueStore` antes do `fetch`, e recusar submeter de novo o mesmo hash sem
`resume` antes.

## 3. `runResume` perde `remote` e `postHash` — o caminho grátis some

`tools/pixellab-pipeline/src/generate.ts:417-427`, comparado com `:325-344`

O `generate` bem-sucedido grava a entrada completa no lockfile, com `remote: { kind, id, ephemeral }`
e `postHash`. O `runResume` grava uma entrada **incompleta**:

```ts
lock.assets[record.assetId] = {
  specHash: record.specHash,
  postHash: existing?.postHash ?? '',   // ← '' quando o asset nunca esteve no lock
  endpoint: record.endpoint,
  status: 'generated',
  generatedAt: record.completedAt ?? new Date().toISOString(),
  costUsd: record.costUsd,
  artifacts,
  ...(record.jobId ? { jobId: record.jobId } : {}),
  //  ← sem `remote`, apesar de `record.resourceId` existir
};
```

Duas consequências, ambas em `catalog.ts:decide()`:

- **`remote` ausente** → `catalog.ts:404` (`rule.remoteCacheable && entry.remote && …`) nunca é
  verdadeiro para um asset recuperado. Se o artefato local se perder depois, o plano cai em
  `generate` — **pago** — em vez de `redownload` — **grátis** — mesmo com o recurso remoto vivo.
- **`postHash: ''`** → `catalog.ts:395` compara `entry.postHash === asset.postHash` e nunca casa. Todo
  asset recuperado fica permanentemente em `reprocess`. Custo zero, mas é um estado que nunca cicatriza.

`LEITURA`. O teste `resume re-polls existing jobs and never resubmits`
(`src/generate.test.ts`) passa, mas afirma só o que o nome diz: que não houve resubmissão. Não afirma
nada sobre o conteúdo da entrada de lockfile que o `resume` escreveu — que é onde está o defeito.

## 8. `map-builder` tem um tsconfig que impede seus próprios testes de compilar

`tools/map-builder/tsconfig.json:22` (`"types": []`) com `:24` (`"include": ["src/**/*.ts"]`)

`types: []` desliga `@types/node`. `include` puxa `src/**/*.ts`, o que inclui

distintos têm uma causa só.

**Reparo mais curto:** `"types": ["node"]` e excluir `*.test.ts` do tsconfig do browser, ou um
tsconfig separado para os testes — que é o que `iso-core` já faz.

## 26. `WeightedSemaphore.release` pode admitir além da capacidade

`tools/pixellab-pipeline/src/queue.ts:132-152`

`acquire()` subtrai `#available` **depois** do `await`, ou seja, num microtask posterior ao
`waiter.resolve()`. Se dois `release()` acontecerem no mesmo turno antes de os despertados rodarem, o
segundo enxerga um `#available` que ainda não foi debitado pelo primeiro e libera outro waiter.
`#available` pode ficar negativo e mais jobs correm em paralelo do que o tier permite — o que rende
429.

`LEITURA`, não reproduzi. Para reproduzir seria preciso um teste que dispare dois `release` síncronos
com waiters pendentes; os dois testes existentes (`does not deadlock with a job heavier than
capacity`, `respects capacity for light jobs`) não exercitam esse intercalamento.

**Reparo mais curto:** debitar `#available` dentro do `release`, antes do `resolve`, em vez de depois
do `await` no `acquire`.
