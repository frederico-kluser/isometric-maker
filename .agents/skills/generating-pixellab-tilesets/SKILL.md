# Generating PixelLab tilesets

## When to use

Before generating terrain, and before writing the code that places the tiles. Placement is where
this family goes wrong: the generation succeeds and the map still has seams, because the tiles were
indexed by the wrong field.

## Injected knowledge

### Four unrelated families share one tag

`node $S tag "Create map"` returns 18 endpoints across four pipelines that do not interoperate:

| Family | Create | Retrieve | Shape |
|---|---|---|---|
| Top-down Wang | `/create-tileset`, `/tilesets` | `GET /tilesets/{tileset_id}` | two terrains, corner autotiling |
| Sidescroller | `/create-tileset-sidescroller`, `/tilesets-sidescroller` | `GET /tilesets-sidescroller/{tileset_id}` | one platform material, always side view, always transparent |
| Isometric tile | `/create-isometric-tile` | `GET /isometric-tiles/{tile_id}` | a **single** tile, not a set |
| Tiles Pro | `/create-tiles-pro` | `GET /tiles-pro/{tile_id}` | hex / iso / octagon / square variations, road and building kits |

`/tilesets` and `/create-tileset` take the same request body; `/tilesets` is the always-async form.
Fetching a sidescroller tileset from the top-down route returns **404**, not a helpful error.

### Wang autotiling is on the vertex grid, not the cell grid

This is the part that no amount of staring at the images will teach you. Terrain is defined per
**vertex**: a map of W×H cells has (W+1)×(H+1) vertices, each holding one terrain value. Each cell
reads its four corner vertices (NW, NE, SW, SE) and you place the tile whose pattern matches. Because
adjacent cells share vertices, tiles connect seamlessly by construction — you never need edge
matching logic.

Match on **`pattern_4x4`**, not on `corners`. `pattern_4x4` encodes terrain as `0=lower`, `1=upper`,
`2=transition`, `255=wildcard`; `row_1` and `row_2` hold the four corners while `row_0` and `row_3`
hold the terrain above and below. `connections` is **deprecated and not populated** for new top-down
tilesets — code written against it silently gets nothing.

### The tile count changes with `transition_size`, and the extras are ambiguous

`transition_size` ∈ 0, 0.25, 0.5, 1. At **1.0** the tileset returns **25 tiles instead of 16**,
corners take a third value `transition`, and a cliff wall occupies the cell **below** the terrain
boundary — so a cliff spans two map rows.

Those 25 tiles cover only **21 distinct corner combinations**: four wall-continuation tiles share
their corners with a twin. Select by `pattern_4x4` or the twins collapse into one another and the
cliff renders wrong.

Do not hardcode either count. The retrieval endpoint's own guidance is to read `total_tiles` or the
length of `tiles`, because the route also serves tilesets generated by earlier versions that report
other counts at `transition_size=1.0`.

### Sizes and modes, per family

- Top-down and sidescroller `tile_size`: **16 or 32**. `64` exists in the enum but **requires
  `mode='pro'`** (`tools/pixellab-pipeline/src/endpoints.ts:150@b6e61f99`).
- `spread_x`, `slope_size` and `raggedness` are **Pro only** and are silently inert in standard mode.
- Isometric tile: 16–64, and the spec notes sizes above 24 usually look better. `isometric_tile_size`
  ∈ 16, 32; `isometric_tile_shape` ∈ thin tile, thick tile, block — thickness controls how much
  height variation the map can express.
- Tiles Pro: `tile_size` 16–256, 32 recommended.

### The isometric tile has no proportion parameter — `init_image` is the only lever

`/create-isometric-tile` cannot be told how tall the block is. `isometric_tile_shape` is the closest
thing, and the spec describes it only as "~15%, ~25%, ~50% of canvas height". Measured across the five
paid blocks in this project (48×48, `shape='block'`): the top diamond came out 2:1 in all five, and
the **vertical edge varied between 20 and 22 px** block to block. Blocks that do not share a height do
not stack.

What the endpoint does have is `init_image` plus `init_image_strength` (integer 1–999, default 300).
That is the lever this project uses, **chained**: the code-drawn cube mould opens the first face, and
that face's RESULT becomes the `init_image` (and `color_image`) of the remaining three views — every
block ships four distinct views, one per camera rotation
(`docs/adr/0029-quatro-vistas-molde-encadeado-e-rotate.md`, superseding ADR 0022/0025). A second
technique routes the same first face through `/create-character-v3` as `reference_image` and derives
the four views from the character's `rotation_urls` — the two are cached separately to be compared.

Two traps ride along:

- **`init_image_strength` has inverted polarity versus Stable Diffusion.** It sets how much noise is
  added before generation, so **higher means closer to the reference**. Anyone applying
  `denoising_strength` intuition tunes it backwards.
- **`style_image` and `style_strength` do not exist on this endpoint**, and its request schema
  declares `additionalProperties: false` — sending them is a rejection, not a silent ignore. They do
  exist on `/create-image-bitforge`, `/generate-image-v2`, `/create-tiles-pro` and others in the same
  API, which is exactly what makes assuming them here so easy.

A geometrically true cube in 2:1 dimetric has vertical edge `d = W·√6/4 ≈ 0.6124·W`, so a correct cube
sprite is ~11% taller than square — never `W/2`
(`packages/iso-core/src/iso-cube.ts`, `docs/adr/0024-cubo-isometrico-canonico.md`).

### Perspective on tilesets is a narrower enum than everywhere else

The tileset enum is narrower than the general one: `TilesetCameraView` = low top-down, high top-down

There is no `side` — the sidescroller family exists precisely because side view is a different
pipeline, and its view is fixed and cannot be changed.

The project standard is `low top-down` (`docs/adr/0005-low-top-down-8-direcoes.md:19@0f447499`), and
the endpoint default is **high top-down**. Omitting `view` puts the terrain in a different
perspective from the characters, with no error.

### Tiles Pro is a different mental model

It draws tile-shape outlines and has the model fill them, so it produces **variations** rather than a
connected set — unless you ask otherwise. `tile_feature` switches that: `roads` produces 18-config
path autotiles, `tileset` produces corner Wang terrain transitions, `building` produces wall/floor
kits. The response's `kind` field tells you which you got, and `tile_rules` carries the placement
rules (`rule_type` edge / corner / outline) — null for plain variations.

Prompting tip from the spec itself: number each variation in the description —
`"1). grass tile 2). dirt tile 3). stone tile"` — for control over which is which.

Results come back as `storage_urls`, a map like `{"tile_0": "...", "tile_1": "..."}`, not as inline
base64 like the other families.

### Retrieval quirks

All four families are asynchronous. `/create-tileset` and `/create-isometric-tile` declare **both
`200` and `202`** and may answer either — branch on the body, not the code
(see `orchestrating-pixellab-jobs`). Retrieval returns **423** while still generating, with
`Retry-After`. `DELETE /tiles-pro/{tile_id}` returns **409** while the tile is still generating.

```bash
S=.agents/skills/querying-pixellab-api/scripts/inspect-spec.mjs
node $S endpoint /create-tileset
node $S response /tilesets/{tileset_id}
node $S flow /create-tiles-pro
```

### What the guides do not give you

The public guide at `pixellab.ai/docs/guides/map-tiles` is a **plugin UI tutorial**, not API
documentation: it covers selections and inpaint layers in the editor and contains no endpoint,
parameter or code. Everything above comes from the vendored spec
(`tools/pixellab-pipeline/openapi/openapi-v2.json:1@8bc0acb9`).
